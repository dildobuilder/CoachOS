# Sprint 1F - Training Plans & Planned Workouts

## Goal

Add the first planning layer for CoachOS:

`training plan -> planned workout -> scheduled calendar event -> workout session -> completed history`

The main decision is to keep plan and actual data separate. `planned_workouts` may exist without `calendar_event_id`; they are visible in the client calendar but do not appear in the trainer calendar until a time is assigned.

## Scope

Sprint 1F includes:

- `training_plans`;
- `planned_workouts`;
- `planned_exercises`;
- `planned_sets`;
- 4-week default client plan creation;
- planned workout generation by selected weekdays;
- adding exercise-base exercises and planned sets to planned workouts;
- assigning time to planned workouts through one `calendar_event`;
- starting a scheduled planned workout as a prefilled `workout_session`;
- planned-to-actual links for future comparison.

Sprint 1F does not include reusable templates, template tables, drag-and-drop, advanced periodization, automatic progression, AI, nutrition, client portal, PR tracking, tonnage analytics, or plan-vs-actual charts.

## Database Model

All planned tables include `trainer_id` for the standard CoachOS RLS/debug pattern.

`training_plans.status`:

- `active`;
- `completed`;
- `archived`.

`planned_workouts.status`:

- `planned`;
- `scheduled`;
- `in_progress`;
- `completed`;
- `cancelled`.

Relation model:

- `planned_workouts.calendar_event_id` links a planned workout to a scheduled calendar slot.
- `calendar_events.planned_workout_id` is not added.
- `workout_sessions.planned_workout_id`, `session_exercises.planned_exercise_id`, and `session_sets.planned_set_id` preserve future planned-vs-actual comparison.

Database duplicate protection:

```sql
create unique index planned_workouts_calendar_event_id_unique
on public.planned_workouts(calendar_event_id)
where calendar_event_id is not null;
```

## Scheduling

If a planned workout has no `calendar_event_id`, `Назначить время` creates a `client_training` event after Sprint 1C conflict detection.

If a planned workout already has `calendar_event_id`, Sprint 1F does not create a second event. The UI shows that the workout is already scheduled, and repeated scheduling is blocked with a clear message.

## Starting Planned Workout

`startWorkoutFromEvent` remains the single entrypoint.

When the event is linked to a planned workout and no session exists:

1. Create `workout_sessions` with `planned_workout_id`.
2. Copy `planned_exercises` into `session_exercises`.
3. Copy `planned_sets` into `session_sets`.
4. Save planned-to-actual ids.
5. Mark the planned workout as `in_progress`.

Completing the session marks the linked planned workout as `completed`.

## UI

Routes:

- `/clients/[clientId]/plans`;
- `/clients/[clientId]/plans/new`;
- `/clients/[clientId]/plans/[planId]`;
- `/clients/[clientId]/planned-workouts/[plannedWorkoutId]`.

Client navigation adds `Планы`.

Client calendar shows unscheduled planned workouts as plan cards without time. Scheduled planned workouts are represented by their linked `calendar_events` to avoid duplicate display.

## Acceptance Criteria

- migrations apply successfully;
- planned tables exist with `trainer_id`;
- planned statuses match the allowed values;
- RLS protects planned data by trainer ownership;
- trainer can create a 4-week plan;
- planned workouts are generated by selected weekdays;
- unscheduled planned workouts appear in client calendar only;
- scheduled planned workout creates exactly one `calendar_event`;
- repeated scheduling does not create a duplicate event;
- conflict detection works when scheduling;
- scheduled planned workout appears in trainer calendar;
- starting scheduled planned workout creates a prefilled session;
- planned exercises/sets map to actual exercises/sets;
- duplicate session protection remains intact;
- Sprint 1C calendar remains stable;
- Sprint 1D exercise base remains stable;
- private preview auth remains stable;
- `pnpm typecheck`, `pnpm lint`, and `pnpm build` pass.

## Manual QA

1. Create a 4-week plan for a client.
2. Select Monday/Wednesday/Friday.
3. Verify planned workouts are generated on correct dates.
4. Verify unscheduled planned workouts appear in client calendar.
5. Verify unscheduled planned workouts do not appear in trainer calendar.
6. Add exercise-base exercises and planned sets.
7. Assign time to one planned workout.
8. Verify one `calendar_event` is created.
9. Try assigning time again and verify no duplicate event is created.
10. Try scheduling into a busy slot and verify conflict error.
11. Start the scheduled workout.
12. Verify the session is prefilled.
13. Complete the session.
14. Verify completed session opens readonly.
15. Verify Sprint 1C calendar, Sprint 1D exercise base, private preview auth, and duplicate session protection still work.

## Risks

- Duplicate planned scheduling: mitigated by app guard and partial unique index.
- Calendar sync drift: mitigated by one-way relation from planned workout to event.
- Template scope creep: templates deferred to Sprint 1F-b.
- Start workout regression: `startWorkoutFromEvent` stays the single entrypoint.
- RLS mistakes: every planned table has `trainer_id` and parent ownership policies.
